# Huffman Coding: An In-Depth Explanation

## 1. Introduction

Huffman coding is a lossless data compression algorithm that reduces the amount of space required to represent information without losing any information. It was developed by David A. Huffman in 1952 while he was a graduate student at MIT. Huffman coding is one of the classic examples of a greedy algorithm and is widely used as a building block in compression systems.

The central idea behind Huffman coding is simple:

Symbols that occur frequently should be represented using fewer bits, while symbols that occur less frequently can be represented using more bits.

Consider a text containing only four symbols: A, B, C, and D. If every symbol occurs equally often, there is little advantage in giving one symbol a shorter representation than another. However, suppose A occurs very frequently while D occurs only occasionally. We can assign a short code to A and longer codes to B, C, and D. Since A appears frequently, the total number of bits required to represent the entire message can be reduced.

Huffman coding is a variable-length prefix coding technique. The codes generated by Huffman coding have an important property called the prefix property: no valid code is a prefix of another valid code. This property allows the compressed bitstream to be decoded unambiguously without separators between individual symbols.

For example, consider the following codes:

A = 0
B = 10
C = 110
D = 111

The code for A is 0, the code for B is 10, the code for C is 110, and the code for D is 111. None of these codes is a prefix of another code. Therefore, a stream such as 0101110 can be decoded uniquely.

Huffman coding is therefore based on three important ideas:

1. Count how frequently each symbol occurs.
2. Construct a binary tree based on those frequencies.
3. Assign shorter bit sequences to more frequent symbols and longer bit sequences to less frequent symbols.

The resulting representation is lossless because every original symbol can be recovered exactly.

---

## 2. Why Compression Is Possible

Suppose a file contains only the symbols A, B, C, and D.

A straightforward fixed-length representation would require two bits per symbol:

A = 00
B = 01
C = 10
D = 11

Because there are four possible symbols, two bits are sufficient to represent every symbol.

Now suppose the frequencies are:

A = 70
B = 15
C = 10
D = 5

Using fixed-length coding, every symbol still requires two bits. For 100 symbols, the total would therefore be:

100 × 2 = 200 bits.

However, A occurs 70 percent of the time. We would like to represent A using fewer bits.

A possible prefix code is:

A = 0
B = 10
C = 110
D = 111

The number of bits required is:

A: 70 × 1 = 70
B: 15 × 2 = 30
C: 10 × 3 = 30
D: 5 × 3 = 15

The total is:

70 + 30 + 30 + 15 = 145 bits.

The original fixed-length representation required 200 bits, while the Huffman representation requires only 145 bits, ignoring the additional metadata required to store the coding information.

This demonstrates the basic principle of Huffman coding: frequent symbols receive short codes and infrequent symbols receive long codes.

---

## 3. Prefix Codes

The prefix property is fundamental to Huffman coding.

A code is a prefix of another code if the first code appears completely at the beginning of the second code.

For example:

A = 0
B = 01

Here, A's code, 0, is a prefix of B's code, 01.

This is problematic because a bitstream such as 01 could be interpreted as either:

A followed by something else

or

B

There would be ambiguity.

Huffman coding avoids this problem by constructing a prefix-free code.

Consider:

A = 0
B = 10
C = 110
D = 111

Here:

0 is not a prefix of 10, 110, or 111.

10 is not a prefix of 110 or 111.

110 is not a prefix of 111.

Therefore, the codes are prefix-free.

This means the decoder can process the bitstream from left to right. Once it reaches a complete code, it knows exactly which symbol has been represented.

---

## 4. The Huffman Tree

Huffman codes can be represented naturally using a binary tree.

Each symbol is stored at a leaf of the tree.

Moving to the left child represents a bit of 0.

Moving to the right child represents a bit of 1.

Consider the following tree:

```
             Root
            /    \
           A      Node
                 /    \
                B      Node
                      /    \
                     C      D
```

The paths from the root to each symbol produce the codes:

A = 0
B = 10
C = 110
D = 111

The path to A contains one edge, so its code has length one.

The path to B contains two edges, so its code has length two.

The paths to C and D contain three edges, so their codes have length three.

This explains an important property of Huffman coding:

Frequent symbols tend to be placed closer to the root, while less frequent symbols tend to be placed farther away.

The depth of a leaf in the Huffman tree is exactly the length of the code assigned to that symbol.

---

## 5. Constructing the Huffman Tree

The Huffman tree is constructed using a greedy algorithm.

The algorithm begins with a collection of leaf nodes, one for every symbol that occurs in the input.

Each leaf contains:

* The symbol
* The frequency of that symbol
* A pointer to its left child
* A pointer to its right child

Initially, every symbol is an independent tree containing a single node.

Suppose the frequencies are:

A = 5
B = 9
C = 12
D = 13
E = 16
F = 45

The algorithm repeatedly combines the two nodes with the smallest frequencies.

A priority queue, usually implemented as a min-heap, is commonly used to efficiently find the two smallest nodes.

Initially the priority queue contains:

5, 9, 12, 13, 16, 45

The two smallest values are 5 and 9.

Combine them:

5 + 9 = 14

Create a new internal node with frequency 14. Its children are the nodes with frequencies 5 and 9.

The queue now contains:

12, 13, 14, 16, 45

Again, select the two smallest:

12 and 13

Combine them:

12 + 13 = 25

The queue becomes:

14, 16, 25, 45

Again select:

14 and 16

Combine them:

14 + 16 = 30

The queue becomes:

25, 30, 45

Combine 25 and 30:

25 + 30 = 55

The queue becomes:

45, 55

Finally combine 45 and 55:

45 + 55 = 100

The final node is the root of the Huffman tree.

The root frequency is equal to the total number of symbols in the input.

---

## 6. Why the Two Smallest Nodes Are Combined

The greedy choice made by Huffman's algorithm is to combine the two symbols or subtrees with the smallest frequencies.

Why?

A symbol at greater depth receives a longer code. Therefore, symbols that occur infrequently can tolerate being placed deeper in the tree.

Symbols that occur frequently should remain closer to the root.

The two least frequent items are therefore the best candidates to receive additional depth.

After combining them, the resulting subtree can be treated as a single item with frequency equal to the sum of its children's frequencies.

This is what makes the greedy algorithm work.

At every step, the algorithm chooses the two smallest weights, combines them, and inserts the combined weight back into the collection.

---

## 7. Priority Queue and Min-Heap

A priority queue is an important data structure for an efficient Huffman implementation.

The priority queue stores nodes ordered by their frequency.

The node with the smallest frequency must be accessible efficiently because every step of the Huffman algorithm requires the two smallest nodes.

A min-heap is a natural implementation.

In a min-heap, the smallest element is stored at the root.

For a zero-indexed array representation:

left child = 2 * index + 1

right child = 2 * index + 2

parent = (index - 1) / 2

The important property is:

parent frequency <= child frequency

The heap does not completely sort all elements. It only guarantees that the minimum element is at the root.

For Huffman coding, the main operations are:

push a node into the heap

pop the minimum-frequency node

The time complexity of each operation is O(log n).

Since there are at most n initial symbols and approximately n - 1 internal nodes, constructing the Huffman tree using a priority queue takes O(n log n) time.

For a byte-oriented compressor, there are only 256 possible symbols, so the number of nodes is very small. However, using a priority queue is still conceptually important because it demonstrates the standard Huffman algorithm.

---

## 8. Generating Huffman Codes

After constructing the Huffman tree, codes can be generated by traversing the tree.

Start at the root with an empty code.

Whenever the traversal moves left, append a 0.

Whenever the traversal moves right, append a 1.

For example:

```
             Root
            /    \
           A      *
                 / \
                B   C
```

The traversal produces:

A:
Root → left

Therefore:

A = 0

B:
Root → right → left

Therefore:

B = 10

C:
Root → right → right

Therefore:

C = 11

A recursive tree traversal is a natural way to generate these codes.

If the current code is represented by the integer code and its length is represented by length, moving left can be implemented as:

code = code << 1

Moving right can be implemented as:

code = (code << 1) | 1

The length is incremented after moving to a child.

For example, suppose the current code is binary 10.

Moving left produces:

10 → 100

Moving right produces:

10 → 101

This process continues until a leaf is reached.

When a leaf is reached, the accumulated bit sequence is stored as the Huffman code for that symbol.

---

## 9. Encoding the Input

Once the Huffman code table has been generated, compression becomes straightforward.

Read each byte from the original input file.

Use that byte as an index into the Huffman code table.

Retrieve the corresponding Huffman code.

Write the bits of that code to the compressed output.

For example, suppose:

A = 0
B = 10
C = 110
D = 111

and the input is:

ABCD

The encoded bitstream becomes:

0 10 110 111

which gives:

010110111

The important point is that the compressed stream is not naturally byte-aligned.

The encoded sequence may contain any number of bits.

For example, the final compressed sequence might contain 19 bits rather than a multiple of eight.

Therefore, a file compressor needs a bit-level output mechanism.

---

## 10. Bit-Level File I/O

Normal file I/O is generally byte-oriented.

Functions such as fgetc and fputc operate on bytes.

Huffman codes, however, are sequences of individual bits.

A BitWriter can solve this problem by maintaining a temporary byte-sized buffer.

Suppose the encoder wants to write:

101101

The BitWriter places these bits into its buffer:

101101

After eight bits have accumulated, the complete byte is written to the file.

If the final buffer contains fewer than eight bits, the remaining positions can be filled with padding bits.

For example:

101101

can be padded with zeros:

10110100

The resulting byte can then be written to the file.

The decoder must know when the real data ends so that it does not interpret padding bits as actual encoded data.

---

## 11. Handling Padding Bits

Padding is an important issue in a real Huffman file format.

Suppose the actual encoded data contains:

101101

A file cannot normally write only six bits. It writes complete bytes.

Therefore, the compressor might store:

10110100

The final two zeros are padding.

If the decoder simply read every bit until the physical end of the file, it might incorrectly interpret the padding as another Huffman code.

One solution is to store the number of valid bits in the final byte.

Another solution is to store the original number of symbols.

If the decoder knows that the original file contained exactly 1000 symbols, it can stop decoding once it has reconstructed exactly 1000 symbols.

The remaining bits in the final byte can safely be ignored.

This is a useful technique because it avoids having to store the number of padding bits separately.

---

## 12. Storing Metadata

A compressed file needs more than just the compressed bitstream.

The decoder needs enough information to understand the encoding.

One possible file structure is:

Magic number
Frequency table
Compressed bitstream

The magic number identifies the file format.

For example, a compressor might begin every file with:

HUF1

The frequency table contains the frequency of every possible byte.

If there are 256 possible byte values and every frequency is stored as a 64-bit integer, the frequency table requires:

256 × 8 = 2048 bytes

The magic number adds another four bytes.

Therefore, the header in such a simple format requires:

2052 bytes

before the compressed data begins.

The decompressor reads this header and reconstructs the Huffman tree.

---

## 13. Why Store Frequencies Instead of the Tree?

There are multiple ways to store Huffman metadata.

One possibility is to serialize the entire Huffman tree.

Another possibility is to store the frequencies and rebuild the tree.

Storing frequencies is conceptually simple because the frequency table completely determines the inputs to the Huffman construction algorithm.

The decompressor can read the frequency table and run the same tree construction algorithm.

However, this approach introduces an important requirement:

The tree construction must be deterministic.

If two symbols have equal frequencies, there can be multiple valid Huffman trees.

Therefore, if a compressor stores only frequencies, both the compressor and decompressor must use exactly the same tie-breaking rules.

Otherwise, the compressor and decompressor might construct different trees.

---

## 14. Equal Frequencies and Tie-Breaking

Huffman coding does not necessarily produce a unique tree.

Suppose:

A = 1
B = 1
C = 1
D = 1

There are several possible optimal Huffman trees.

One tree might produce:

A = 00
B = 01
C = 10
D = 11

Another equally optimal tree might produce:

C = 00
D = 01
A = 10
B = 11

Both trees have the same compression cost.

The problem appears when the compressor and decompressor independently rebuild the tree.

If the compressor chooses one tree and the decompressor chooses another, the same compressed bit sequence can be interpreted differently.

Therefore, an implementation that stores only frequencies needs a deterministic tie-breaking rule.

A common solution is to define a secondary ordering criterion for nodes when frequencies are equal.

For example, nodes can be ordered by:

1. Frequency
2. A deterministic symbol or subtree ordering

Another common approach in real compression formats is to use canonical Huffman codes.

---

## 15. Canonical Huffman Codes

Canonical Huffman coding is a way of representing Huffman codes so that the exact bit patterns can be reconstructed deterministically from the code lengths.

The Huffman algorithm first determines the length of the code assigned to each symbol.

For example:

A → length 2
B → length 1
C → length 3
D → length 3

The exact original bit patterns do not need to be stored.

Instead, the decoder can use the code lengths and a deterministic ordering of symbols to reconstruct the actual codes.

Canonical codes have useful properties.

Codes of the same length are assigned consecutive numerical values.

Shorter codes appear before longer codes according to the canonical construction.

Symbols are ordered deterministically.

Therefore, both encoder and decoder can construct exactly the same codes.

Canonical Huffman coding is used in several practical compression formats and is an important technique in real-world compression systems.

---

## 16. Huffman Encoding and Decoding

The encoder and decoder perform inverse operations.

During encoding:

Original symbol
→ Huffman code
→ bitstream

During decoding:

Bitstream
→ Huffman tree traversal
→ original symbol

Suppose the codes are:

A = 0
B = 10
C = 110
D = 111

The encoder converts:

ABCD

into:

010110111

The decoder reads bits from left to right.

It starts at the root.

A bit of 0 means move left.

A bit of 1 means move right.

When a leaf is reached, the corresponding symbol is output and the decoder returns to the root.

For:

010110111

the decoder sees:

0 → A

10 → B

110 → C

111 → D

Therefore:

010110111

becomes:

ABCD

The prefix-free property guarantees that the decoding process is unambiguous.

---

## 17. Why Decoding Is Unambiguous

Consider the code:

A = 0
B = 10
C = 110
D = 111

Suppose the compressed stream is:

010111

The decoder begins at the root.

The first bit is 0, so it moves left and reaches A.

Therefore the first symbol is A.

The decoder returns to the root.

The remaining stream is:

10111

The first bit is 1, so it moves right.

The next bit is 0, so it moves left and reaches B.

Therefore the next symbol is B.

The remaining stream is:

111

The decoder follows right, right, right and reaches D.

Therefore the result is:

ABD

There is no need for separators between codes.

This is one of the major advantages of prefix coding.

---

## 18. Huffman Coding as a Greedy Algorithm

Huffman coding is a classic greedy algorithm.

A greedy algorithm makes a locally optimal choice at each step with the expectation that these choices lead to a globally optimal solution.

In Huffman's algorithm, the greedy choice is:

Select the two nodes with the smallest frequencies and merge them.

The combined node is inserted back into the priority queue.

This process is repeated until only one node remains.

The final tree minimizes the weighted path length among binary prefix codes for the given symbol frequencies.

The cost of a Huffman tree can be expressed as:

Cost = sum over all symbols of:

frequency(symbol) × code_length(symbol)

For a symbol appearing 100 times with a code length of 2, its contribution to the total cost is:

100 × 2 = 200 bits

Huffman coding attempts to minimize this total cost.

---

## 19. Huffman Coding and Optimality

For a known set of symbol frequencies, Huffman's algorithm produces an optimal binary prefix code.

This does not necessarily mean that the compressed file will always be smaller than the original file.

The reason is that the compressed file must also contain metadata.

For example, a simple implementation that stores a 2052-byte frequency table has a substantial overhead.

If the original input file is only 100 bytes, adding a 2052-byte header makes compression counterproductive.

For large files, however, the header becomes relatively small compared with the compressed data.

Therefore, practical compression systems use more compact ways of storing the coding information.

---

## 20. Time Complexity

Let n represent the number of distinct symbols.

Building the initial collection of nodes requires O(n) time.

Using a binary min-heap, each extraction and insertion takes O(log n) time.

There are approximately n - 1 merging operations.

Therefore, constructing the Huffman tree takes:

O(n log n)

time.

Generating codes requires visiting each tree node:

O(n)

time.

Encoding the input requires reading each input symbol once:

O(N)

where N is the number of symbols in the input.

Therefore, for a fixed alphabet, the dominant cost is generally the processing of the input data.

For byte-oriented files, the alphabet has only 256 possible symbols, so n is bounded by 256.

---

## 21. Space Complexity

The frequency table requires space proportional to the alphabet size.

For byte-oriented Huffman coding:

256 frequency values are required.

The Huffman tree contains at most:

2n - 1

nodes when there are n distinct symbols.

For 256 symbols, the maximum number of tree nodes is:

2 × 256 - 1 = 511

The code table requires one entry for every possible symbol.

Therefore, the data structures required for the Huffman tree and coding table are small for a byte-oriented compressor.

The main memory requirement can instead come from the input data if the implementation chooses to load the entire file into memory. A streaming implementation can avoid this by reading the input in passes.

---

## 22. Two-Pass Compression

A simple Huffman file compressor can operate using two passes over the input.

During the first pass:

1. Open the input file.
2. Read every byte.
3. Count the frequency of every byte.
4. Construct the Huffman tree.
5. Generate the Huffman codes.

During the second pass:

1. Return to the beginning of the input file.
2. Read every byte again.
3. Look up its Huffman code.
4. Write the corresponding bits to the output.

This approach is simple and avoids storing the entire input file in memory.

The two-pass approach is particularly suitable for a learning project because the stages are clearly separated.

The first pass analyzes the data.

The second pass performs the actual encoding.

---

## 23. Binary Files Versus Text Files

Huffman coding does not fundamentally operate on characters such as letters or words.

A byte-oriented Huffman compressor can treat every possible byte value from 0 through 255 as a symbol.

This means the same algorithm can compress:

text files

images

executables

audio data

binary databases

and other arbitrary binary files.

However, the effectiveness of Huffman coding depends on the statistical distribution of the input.

If the input already has a nearly uniform distribution of byte values, Huffman coding may provide little compression.

If the input contains strong frequency differences between symbols, Huffman coding can provide better compression.

Huffman coding is therefore a general lossless compression technique rather than a text-only algorithm.

---

## 24. Compression Ratio

A useful measurement for a compressor is the compression ratio.

One possible definition is:

Compression ratio = compressed size / original size

Suppose the original file is:

1,000,000 bytes

and the compressed file is:

600,000 bytes.

Then:

compression ratio = 600,000 / 1,000,000 = 0.60

Another commonly used measurement is the percentage reduction:

reduction = 1 - compressed size / original size

In this example:

reduction = 1 - 0.60 = 0.40

Therefore, the file was reduced by 40 percent.

When evaluating a Huffman implementation, the header size must be included. A compressor that reports only the size of the encoded bitstream but ignores its metadata can give a misleading compression result.

---

## 25. Limitations of Huffman Coding

Huffman coding is powerful, but it has limitations.

First, the frequency distribution must be known or estimated before constructing the tree.

A simple implementation therefore requires two passes over the input.

Second, Huffman coding operates on individual symbols and does not directly exploit repeated sequences.

For example, a long repeated phrase might be better compressed using a dictionary-based algorithm.

Third, Huffman coding may be ineffective when the symbol distribution is close to uniform.

Fourth, storing the Huffman metadata introduces overhead.

Finally, Huffman coding assigns an integer number of bits to each symbol. It cannot generally represent the ideal information content of every symbol exactly.

For example, if a symbol has probability one third, its ideal information content is approximately:

-log2(1/3) ≈ 1.585 bits

A standard Huffman code might need either 1 or 2 bits for that symbol, because a symbol's code length must be an integer number of bits.

---

## 26. Huffman Coding Compared With Fixed-Length Coding

Fixed-length coding gives every symbol the same number of bits.

If there are 256 possible byte values, fixed-length encoding requires:

8 bits per byte.

Huffman coding instead gives different symbols different code lengths.

For example:

A = 0
B = 10
C = 110
D = 111

The average code length is determined by the frequency distribution.

If A is very common, its one-bit representation significantly reduces the average number of bits per symbol.

Therefore, Huffman coding is especially useful when symbol frequencies are uneven.

---

## 27. Huffman Coding Compared With Other Compression Techniques

Huffman coding is often used as part of a larger compression system rather than as the only compression technique.

Dictionary-based algorithms such as LZ77 and LZ78 exploit repeated sequences.

Run-length encoding exploits consecutive repetitions.

Arithmetic coding represents an entire sequence using a fractional interval and can approach the theoretical entropy more closely in some cases.

Modern formats often combine techniques.

For example, a system may first transform the input to expose redundancy and then use Huffman coding to efficiently represent the resulting symbols.

Therefore, Huffman coding is best understood not only as a complete compression algorithm but also as a fundamental component of many compression systems.

---

## 28. Entropy

The theoretical lower bound for lossless compression is related to information entropy.

For a source with symbol probabilities p1, p2, ..., pn, the entropy is:

H = -sum p(i) log2 p(i)

Entropy represents the average amount of information carried by a symbol under the assumed probability distribution.

Huffman coding produces an average code length that is close to the entropy.

For a binary Huffman code, the average code length L satisfies:

H <= L < H + 1

for an appropriate probability model.

This means that Huffman coding can get within one bit per symbol of the entropy bound for a binary prefix code.

The gap between entropy and average Huffman code length is one reason other techniques, such as arithmetic coding, can sometimes achieve better compression.

---

## 29. A Complete Example

Consider the input:

ABRACADABRA

Count the frequencies:

A = 5
B = 2
R = 2
C = 1
D = 1

The Huffman algorithm repeatedly selects the two smallest frequencies.

First:

C = 1
D = 1

Combine them:

CD = 2

Now:

A = 5
B = 2
R = 2
CD = 2

Several nodes have equal frequencies. A deterministic tie-breaking rule is therefore important for an implementation that reconstructs the tree from frequencies.

Suppose a particular deterministic construction eventually produces the following codes:

A = 0
B = 10
R = 110
C = 1110
D = 1111

The exact codes depend on the tree and tie-breaking rules.

The encoder then replaces every symbol with its code.

The important point is not the exact codes but the relationship between frequency and code length:

A is the most frequent symbol and receives the shortest code.

B and R are less frequent and receive longer codes.

C and D are the least frequent and receive the longest codes.

This reduces the total number of bits required to represent the message.

## 30. The Complete Huffman Compression Pipeline

A practical Huffman compressor can be viewed as a sequence of stages.

Stage 1: Open the input file.

Stage 2: Read the input and calculate the frequency of every possible symbol.

Stage 3: Create one leaf node for every symbol with a nonzero frequency.

Stage 4: Insert all leaf nodes into a min-priority queue.

Stage 5: Remove the two nodes with the smallest frequencies.

Stage 6: Create a new internal node whose frequency is the sum of the two removed nodes.

Stage 7: Insert the new node into the priority queue.

Stage 8: Repeat until only one node remains.

Stage 9: Treat the remaining node as the root of the Huffman tree.

Stage 10: Traverse the tree and generate a code for every symbol.

Stage 11: Write metadata required by the decoder.

Stage 12: Read the input file again.

Stage 13: Replace every input symbol with its Huffman code.

Stage 14: Write the resulting bits using a bit-level output mechanism.

Stage 15: Flush any remaining bits and finish the output file.

The decompression pipeline performs the inverse operations.

Stage 1: Open the compressed file.

Stage 2: Read and validate the file header.

Stage 3: Recover the information needed to reconstruct the coding tree.

Stage 4: Reconstruct the Huffman tree or canonical code table.

Stage 5: Read the compressed bitstream one bit at a time.

Stage 6: Traverse the Huffman tree according to each bit.

Stage 7: When a leaf is reached, output the corresponding symbol.

Stage 8: Return to the root.

Stage 9: Continue until the expected number of original symbols has been reconstructed.

Stage 10: Close the files and release allocated memory.

---

## 31. Implementation Considerations in C

A low-level C implementation of Huffman coding requires careful resource management.

Tree nodes are commonly allocated dynamically using malloc.

Every allocated node must eventually be freed.

A recursive function can be used to free the entire tree:

free left subtree

free right subtree

free current node

This is a post-order traversal.

The priority queue can store pointers to Huffman nodes rather than copying entire nodes.

The priority queue should not normally own the nodes. The Huffman tree owns the nodes after they have been connected into the tree.

This separation of ownership makes memory management easier to reason about.

The bit reader and bit writer also maintain internal buffers because normal file operations are byte-oriented.

Error handling is particularly important in C. File opening, file reading, file writing, memory allocation, and tree construction can all fail.

A robust implementation should check the result of operations such as:

fopen

malloc

fread

fwrite

fgetc

fputc

and should release resources before returning after an error.

---

## 32. The Role of the File Header

A compressed file is not merely a sequence of Huffman bits.

The decoder must know how those bits should be interpreted.

A simple custom Huffman format might therefore look like:

+-------------------------+
| Magic number            |
+-------------------------+
| Frequency table         |
+-------------------------+
| Compressed bitstream    |
+-------------------------+

The magic number identifies the file type.

The frequency table allows the decoder to reconstruct the Huffman tree.

The compressed bitstream contains the actual encoded data.

A more sophisticated format might instead contain:

+-------------------------+
| Magic number            |
+-------------------------+
| Code lengths            |
+-------------------------+
| Compressed bitstream    |
+-------------------------+

The second approach can be combined with canonical Huffman coding and can substantially reduce metadata compared with storing a full frequency table.

## 34. Summary

Huffman coding is a lossless compression algorithm based on variable-length prefix codes.

Its fundamental principle is:

Frequent symbols receive shorter codes.

Infrequent symbols receive longer codes.

The algorithm constructs a binary tree by repeatedly combining the two least frequent nodes.

A min-priority queue makes it efficient to repeatedly retrieve the two smallest nodes.

The final tree determines the Huffman codes.

Moving left represents 0.

Moving right represents 1.

Each symbol is stored at a leaf.

Because Huffman codes are prefix-free, the compressed bitstream can be decoded unambiguously.

A practical file compressor must also solve several engineering problems.

It must store enough metadata for the decoder.

It must handle bit-level I/O even though files are byte-oriented.

It must handle padding in the final byte.

It must manage dynamically allocated memory.

It must detect file and memory errors.

It must ensure that the encoder and decoder agree on the Huffman representation.

Equal frequencies can result in multiple equally optimal Huffman trees, so deterministic tie-breaking or canonical Huffman coding is important when the decoder reconstructs the coding information independently.

The complete conceptual pipeline is:

Input file
→ frequency table
→ Huffman tree
→ Huffman codes
→ encoded bitstream
→ compressed file

and the reverse:

Compressed file
→ metadata
→ Huffman tree or canonical code table
→ bitstream
→ decoded symbols
→ original file

Huffman coding is therefore a compact but rich example of how an algorithm, data structures, bit manipulation, file formats, and systems programming come together to create a working piece of software.
